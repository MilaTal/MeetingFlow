## Итерация 1 — функциональная

1. `same_word`: «Мария» совпадала с «Мариной». Правило Планёрки «хвост ≤ 2 букв» пропускает эту пару и записанный в Планёрке «известный предел» «Алексей ~ Алексейко». Решение: хвост обязан быть падежным окончанием. Обе пары разведены.
2. Вид источника: строки заметок «Повестка: склад» принимались за реплики. Для заметок считаются только реплики с таймкодом.
3. Поиск цитаты окном тянул чужую соседнюю реплику. При равном покрытии берётся самое короткое окно.

## Итерация 2 — LLM-безопасность

1. **Атака Б (расход):** при потолке 0,40 $ прогон потратил 0,75 $ и отчитался «ok». Проверка шла только до вызова, а последний вызов перерасходовал. Решение: прогноз по самому дорогому вызову прогона. Остановка с понятным «Остановлено по пределу».
2. Строка-инъекция без поручения проходила молча. Теперь источник получает карточку `suspicious_source`, встреча не блокируется.
3. Детектор ловил «игнорируй», но не «игнорирует». Расширен до основ.

Атаки А (шаги), А-2 (потолок 0 — ни одного вызова), В (объём — запрос не уходит в модель) сработали с первого раза. В каждом случае реестр не применяется частично.

## Дополнение 03.10.26 — решения Проекта ERP по рекомендациям «единицы и поиск»

Письмо ERP: «Для MeetFlow — решения Проекта ERP по рекомендациям „единицы встречи и поиск“ (03.10.26)». Применено то, что переносимо в базовый проект. Тестов 324, все проходят.

1. **Склейка единиц.** Перед правкой формула ERP (Жаккар ≥ 0,6 на словах от трёх букв) и прежняя формула framework (Жаккар ≥ 0,6 на основах) проверены на 7 парах с известным ответом. Обе ошиблись в одних и тех же местах: «отчёт номер 1 / 2» — 0,67, «регламент приёмки / отгрузки» одного человека — 0,67, «отчёт по браку / по отгрузкам» — 0,60 (всё склеилось бы); настоящий дубль в других падежах — 0,33 (не склеился бы). То есть пункт 2 предыдущего дополнения («заменено Жаккаром») ошибку не закрыл. Новое правило `same_point`: пункты одинаковы, если одна формулировка покрывает другую с точностью до формы слова и на общие слова приходится ≥ 0,6; слово, которое есть своё у каждой стороны, делает их разными. Пары закреплены тестом `test_merge_known_pairs`. Цена та же, что у ERP: пересказ другими словами не склеивается.
2. **Поиск по форме слова.** Правило ERP «с начала слова, хвост ≤ 3 букв, от слова и от основы» — `text.same_lexeme`. Прежняя `same_word` (хвост — только падежное окончание) не находила глаголы: «согласовать» → «согласовали», «принимают» → «принимать». Для имён людей остаётся `same_word`: «Алексей» ~ «Алексейко» в поиске допустимо, в сверке людей — нет.
3. **Поиск по сырой речи** — ключ темы `search.raw_speech`, по умолчанию выключен; вопрос владельцу тематики выводит `meetflow todo`. В теме `erp_rollout` записано решение владельца ERP («не нужен»). Тест, закреплявший поиск по расшифровкам, перевёрнут.
4. **Закрытие по голосу.** Решение и договорённость закрываются только заменой или отменой: «подтвердили…, всё в силе» не закрывает (у ERP 8 из 10 ложных закрытий были такими). Закрытие внутри своей встречи — по ключу темы `units.close_same_meeting`, по умолчанию выключено до замера. Тест «закрывается на той же встрече» перевёрнут в пару «выключено / включено».
5. Остальные пункты письма (задача из единицы через проверки, «не итог» только будущим временем, одна фраза — одна единица, частичный сбой не стирает, имена через `same_word`, ограда данных, проверка даты, номер задачи в поиске) во framework уже были — сверено с кодом.
