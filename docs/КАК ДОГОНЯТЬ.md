## 2. Как переносить одну функцию

1. Найти в Планёрке коммит и запись DECISIONS этой функции. Хэш есть в таблице отставания.
2. Понять смысл правила и перенести его, а не копировать файл. У MeetFlow своё устройство: ядро `meetflow/meetflow/core/`, подсказки `prompts.py`.
3. Сначала тест: перенести тест Планёрки по смыслу. Он должен падать.
4. Правка → тест проходит → полный прогон тестов MeetFlow.
5. Обновить `meetflow/skill/meetflow/SKILL.md`, если правило изменилось.
6. Коммит в `dogonyaem-planerku`: одна функция — один коммит, сообщение «Перенос из Планёрки: <функция> (<хэш Планёрки>)».
7. Строка в `docs/ОТСТАВАНИЕ.md`: «есть», хэш MeetFlow.

## 3. Координация

- **Куда отправлять — только GitHub (слово владелицы 25.10.2026).** Ветка `dogonyaem-planerku` отправляется в `https://github.com/MilaTal/MeetingFlow`, не в GitLab и не в другой удалённый репозиторий. Проверить `git remote -v`: у `origin` должен быть этот адрес; если `origin` указывает на GitLab — `git remote set-url origin https://github.com/MilaTal/MeetingFlow` (или добавить `github` и отправлять в него). Всё, что уже ушло в GitLab, отправить в GitHub той же веткой: `git push origin dogonyaem-planerku`. Проверка: `git ls-remote origin dogonyaem-planerku` совпадает с `git rev-parse HEAD`. В GitLab больше не отправлять. Отчёт об этом — первой строкой в ближайшем `docs/reports/`.
- **Все отчёты — в `P:\Technical\AI Projects\MeetFlow\Отчёты\` (слово владелицы 25.10.2026).** Оттуда их забирает локальная машина Планёрки и отправляет в монорепозиторий (`Рабочее\MeetFlow\`), где их читает разработчик. Поэтому каждый отчёт, ответ и предложение обязательно кладётся копией в эту папку: без двоеточий в имени, без ФИО, ключей и токенов.
- **После каждой группы** — отчёт `docs/reports/Группа N (дата).md` и копия в `P:\Technical\AI Projects\MeetFlow\Отчёты\`. Затем `git push origin dogonyaem-planerku` с повтором: ветку отправлять можно, `main` — только по слову владелицы.
- **Разработчик** раз в день читает ветку, проверяет перенос по смыслу и тесты. Замечания пишет в `docs/ЗАМЕЧАНИЯ (дата).md` в ту же ветку. Перед каждой группой ЛМ сначала исправляет замечания.
- **Новые функции Планёрки** разработчик дописывает в `docs/ОТСТАВАНИЕ.md`.
- **Слияние в `main`** — по группам, после проверки разработчиком и слова владелицы.
- **Платных прогонов моделей нет**: тесты MeetFlow идут без моделей. Если для замера нужна модель — отдельная записка с потолком.
- **Правила:** ФИО в git не писать, без двоеточий в именах файлов, размер отчёта проверять перед коммитом.

## 3а. Правило владелицы 24.10.2026 — ЛМ сама предлагает и берёт правки MeetFlow

Как только ЛМ заканчивает очередной пакет для Планёрки и ERP (развернула, проверила, отправила отчёт), она **сама**:
1. Готовит предложение на правку MeetFlow: что в пакете, что из этого применимо к MeetFlow как к общему фреймворку, что нет — специфика компании или устройства Планёрки — и почему.
2. Оценивает применимость и объём в часах.
3. Применимое заносит строкой в `docs/ОТСТАВАНИЕ.md`: функция, хэш Планёрки, применимо, объём, приоритет. Предложение — файлом `docs/Предложения/<пакет> (дата).md` и копией в `P:\Technical\AI Projects\MeetFlow\Отчёты\`.
4. **Берёт применимое в работу** в ветке `dogonyaem-planerku` по правилу раздела 2, в очередь по приоритету. Разрешения на каждую правку не ждёт. Решение владелицы нужно только для слияния в `main` и для неприменимого, если ЛМ сомневается.

Разработчик тоже дописывает новые функции в таблицу, но ЛМ не ждёт его, а делает это сама после каждого пакета.

**Как чат MeetFlow узнаёт о новом пакете.** Он держит фоновый сторож на монорепозитории ERP_Production_meetings: новые коммиты-отчёты ЛМ по Планёрке и ERP в `main` (записки «Для локальной машины — …» и отчёты в `Рабочее\`). Появился отчёт о развёрнутом пакете — значит, пора готовить предложение по MeetFlow. Чат Планёрки и ERP со своей стороны в конце каждого отчёта пишет строку «Для MeetFlow: <что в пакете, коротко>».
