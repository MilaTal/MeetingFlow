# Итог сборки у каждой версии протокола — `timings` (08.11.2026)

Перенос записки «Правки ERP и Планёрки 03–06.11» (06.11.2026), **п. 12**: «Итог сборки хранить всегда: `timings` у
каждой версии протокола, иначе „почему так вышло“ не воспроизводится». В Планёрке у версии 150 `timings` не было —
оттуда и правило.

## Что сделано

- **Таблица `protocol_versions` получила поле `timings`** (`core/store.py`): сводка сборки версии. Поле добавляется
  само при открытии базы — проверено на копии рабочей: `PRAGMA table_info` показывает `timings` после старта.
- **Сборка пишет итог в свою версию** (`core/pipeline.py`): номер строки версии запоминается при сохранении протокола,
  а в конце прогона — когда итог уже сложился (статус, вызовы, цена, задачи, сроки, источник, проверка, тень) — в
  строку версии пишется JSON итога. Тем же путём, что и очередь сборок: `rep.__dict__`, до 20 тыс. знаков, даты — строкой.
- **Ручные версии тоже с итогом** (`web/app.py`): правка текста — `{"source": "правка вручную", "version": N}`,
  восстановление прежней — `{"source": "восстановлена версия K", "version": N}`. У версий, сохранённых до правки,
  `timings` пустой — читается без ошибки.
- `GET /api/meetings/{id}/protocol/versions` теперь отдаёт `timings` вместе с номером, моделью и датой — экран может
  показать, почему версия такая, без новых запросов.

## Проверки
